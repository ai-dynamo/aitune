This example inspects, tunes, validates and serves the FLUX.1-schnell Diffusers pipeline. YAML files in `recipes/` are
its configuration source. Commands accept `--recipe` (`recipes/single-gpu.yaml` is the default);
model, workload, input, output, GPU, and serving settings are read from that file.

## Recipes and samples

- `recipes/single-gpu.yaml` uses one GPU and is the default recipe.
- `recipes/multi-gpu.yaml` uses two GPUs on one node. Change `execution.gpu_count` if needed.

All paths in a recipe are resolved relative to the YAML file, including `artifact_path`, `output_dir`, and `inputs`.
The model is loaded at the exact `model.revision`.

The `inputs` section selects samples for tuning, validation, and inference. Each JSONL sample has an `id`, a `prompt`,
and a `seed`. The generator is reset to the sample's seed on every call, including original/tuned comparisons during validation.

Generation settings come from `workload`. `execution.gpu_count` must match the number of worker processes, and
`execution.context_parallel` selects `ulysses` or `ring`. `tuning.quantization` optionally includes TorchAO NVFP4 and
FP8 transformer candidates; the supplied recipes leave it disabled. NVFP4 needs compatible Blackwell hardware.

## Build and run a container

### Prerequisites
Before starting the container, sign in to Hugging Face and accept the model's access conditions on the
[FLUX.1-schnell model page](https://huggingface.co/black-forest-labs/FLUX.1-schnell).
Then create a [Hugging Face access token](https://huggingface.co/settings/tokens) for the same account with read access
to the model repository. Export it in the host shell where you will run Docker:

```bash
export HF_TOKEN="hf_your_token_here"
```

The `-e HF_TOKEN` option in the `docker run` command below passes this token into the container for model downloads.

### Building an image

To build a Docker image for the example, run from the repository root:

```bash
docker build -f examples/FluxSchnell/Dockerfile -t aitune-flux-schnell:recipes .
```

### Running a container

Then, enter the container:
```bash
mkdir -p examples/FluxSchnell/results

docker run --rm -it --name aitune-flux-schnell --gpus all --ipc=host \
  -p 127.0.0.1:8080:8080 \
  -e HF_TOKEN -e HF_HOME=/cache/huggingface \
  -v "$PWD/hf-cache":/cache/huggingface \
  -v "$PWD/examples/FluxSchnell/results":/workspace/aitune/examples/FluxSchnell/results \
  aitune-flux-schnell:recipes bash
```
The Dockerfile accepts `--build-arg BASE_IMAGE=...` to reuse a compatible CUDA image with dependencies installed.
The container installs the versions pinned in `uv.lock` in an isolated virtual environment to avoid mixing PyTorch with binary
extensions from the base image. The shell starts in `/workspace/aitune/examples/FluxSchnell`.

Inside the container, synchronize the environment with the example's `uv.lock` before running the workflow:

```bash
uv sync --locked --extra dynamo
```

## Example steps
For a single GPU, run the following commands from within the container. For multiple GPUs, use the explicit
`torchrun` commands in [Multiple GPUs](#multiple-gpus).
```bash
uv run flux_schnell tune --recipe recipes/single-gpu.yaml
uv run flux_schnell validate --recipe recipes/single-gpu.yaml
uv run flux_schnell infer --recipe recipes/single-gpu.yaml
uv run flux_schnell serve --recipe recipes/single-gpu.yaml
```

### Tuning
Tuning compares Torch-TensorRT JIT and TorchInductor JIT for the transformer, plus optional TorchAO candidates.
Module tuning failures abort the command. Before saving, every rank must have a non-eager backend for every
transformer graph; passthrough and eager fallback (including when no candidate beats the baseline) are rejected.
Other discovered modules use AITune's default backend strategy. Maximum-batch-size discovery is disabled to match
the single-image workload. Each rank saves its own checkpoint; rank zero writes `tuned.manifest.json` only after all
ranks have saved. Loading checks the model revision, workload, execution settings, and tuning settings against that
manifest. Checkpoint tensors are staged on CPU to avoid duplicating the weights on the GPU during loading.

### Validation

After tuning, run `flux_schnell validate` to compare original and tuned images using the prompts and seeds from the
sample file selected by `inputs.validation`. Results are saved under the recipe's `output_dir`:

- `validation/{original,tuned}/<sample-id>.png`
- `validation/report.json`, with validation prompts, seeds, RGB SSIM scores, pixel errors, and pass/fail results.

The structural similarity index (SSIM) measures similarity between images generated by the original and tuned models.
`validation.threshold` determines pass/fail; scores below `validation.soft_threshold` produce warnings. A failed hard
threshold makes the command exit unsuccessfully after writing the report.

### Inference

`flux_schnell infer` loads the tuned checkpoint and generates one image per sample in `inputs.inference`, using each
sample's prompt and seed. It runs the pipeline directly, without validation, benchmarking, or a Dynamo deployment.
Images are saved to `output_dir/inference/tuned/<sample-id>.png`. For the single-GPU recipe, the supplied lighthouse
sample produces `results/single-gpu/inference/tuned/lighthouse.png`.

### Benchmarking
There is no benchmark command yet. The recipe's `benchmark.warmup_iterations` still controls tuning inspection
warmup; the other benchmark settings are reserved for future use.

### Dynamo and the prompt UI

It is possible to play with the model and deployment through a simple UI. Run

```bash
uv run flux_schnell serve --recipe recipes/single-gpu.yaml
```

For a single GPU, `serve` keeps Dynamo and the browser UI running until interrupted. Press Ctrl+C to stop it before
running the smoke test, which starts its own deployment on the same port.

Open [http://localhost:8080](http://localhost:8080) when the log prints `Web app:`. Dynamo uses `deployment.port`; the
UI uses `deployment.web_host` and `deployment.web_port`. If you change the web port, update the Docker port mapping.
Both services run inside the container. Model loading and compilation can take several minutes; startup is bounded
by `deployment.readiness_timeout_s`.

The UI allows at most 32 concurrent connections on any bind address and closes excess connections. Request headers
and bodies each have a 10-second read deadline, including clients that send data slowly. Prompt bodies are limited
to 64 KiB. These read deadlines do not include image generation time.

The UI serves the packaged `flux_schnell/dynamo/web.html`. It uses the recipe's dimensions and steps, and chooses a
random seed for each prompt. API clients can send `nvext: {"seed": 123}`; requests without a seed use
`deployment.seed`. Requests must use the recipe's image dimensions and generate one image at a time.

### Dynamo smoke test
For a one-off deployment smoke test, run:

```bash
uv run flux_schnell serve --recipe recipes/single-gpu.yaml --smoke_test
```

This starts Dynamo, waits for readiness, sends `deployment.request_count` requests using `inputs.inference` prompts
and seeds, and saves PNGs and request timings under `output_dir/deployment`. It then shuts Dynamo down. The smoke
test does not start the browser UI.

## Multiple GPUs

Launch worker processes explicitly with `torchrun` on a machine exposing at least two GPUs. Run these commands
inside the container, from `/workspace/aitune/examples/FluxSchnell`:

```bash
uv run torchrun --standalone --nproc-per-node=2 --log-dir logs/tune --tee 3 --local-ranks-filter 0 \
  --module flux_schnell.cli tune --recipe recipes/multi-gpu.yaml
uv run torchrun --standalone --nproc-per-node=2 --log-dir logs/validate --tee 3 --local-ranks-filter 0 \
  --module flux_schnell.cli validate --recipe recipes/multi-gpu.yaml
uv run torchrun --standalone --nproc-per-node=2 --log-dir logs/infer --tee 3 --local-ranks-filter 0 \
  --module flux_schnell.cli infer --recipe recipes/multi-gpu.yaml
```

`--nproc-per-node` must equal the recipe's `execution.gpu_count`. The example checks `WORLD_SIZE` and fails if
they differ; it does not launch additional processes. `--tee 3` saves stdout and stderr for every rank, while
`--local-ranks-filter 0` displays only rank zero in the terminal. Additional visible GPUs are not used.
Each rank configures Diffusers context parallelism, and AITune coordinates distributed tuning and serving.
Only rank zero writes images and reports.

Use the same recipe and GPU count for tuning and serving. The multi-GPU recipe saves separate artifacts under
`results/multi-gpu` and never shares the single-GPU checkpoint.

If a multi-GPU run hangs or reports an NCCL collective timeout, try setting this inside the container before
launching `torchrun` (including in the separate backend terminal when serving):

```bash
export NCCL_P2P_DISABLE=1
```

This disables NCCL's direct GPU-to-GPU (P2P) transport over NVLink or PCIe. It can work around hangs when
peer access is unreliable because of the system's PCIe/IOMMU/ACS configuration, allowing NCCL to use other
transports. Use it as a workaround when needed: disabling P2P can reduce performance. See
[NCCL GPU troubleshooting](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/troubleshooting/gpu_troubleshooting.html).

### Multi-GPU Dynamo deployment

Start the frontend, backend, and UI in separate terminals inside the same container. Open additional shells with
`docker exec -it aitune-flux-schnell bash`. In both the frontend and backend terminals, set:

```bash
export DYN_DISCOVERY_BACKEND=file
export DYN_EVENT_PLANE=zmq
export DYN_REQUEST_PLANE=tcp
export DYN_ROUTER_USE_KV_EVENTS=false
```

In the first terminal, start the frontend. Its port must match `deployment.port` in the recipe:

```bash
uv run python -m dynamo.frontend --http-port 8000
```

In the second terminal, launch the backend ranks:

```bash
uv run torchrun --standalone --nproc-per-node=2 --log-dir logs/serve --tee 3 --local-ranks-filter 0 \
  --module flux_schnell.cli backend --recipe recipes/multi-gpu.yaml
```

Model loading and compilation can take several minutes. Once the backend is ready, start the UI in a third terminal:

```bash
uv run flux_schnell web --recipe recipes/multi-gpu.yaml
```

Open [http://localhost:8080](http://localhost:8080). To send the recipe's smoke-test requests to the running deployment,
use another terminal:

```bash
uv run flux_schnell client --recipe recipes/multi-gpu.yaml
```

Stop each service with Ctrl+C in its terminal. The `flux_schnell serve` command, including `--smoke_test`, is for
single-GPU deployments.
